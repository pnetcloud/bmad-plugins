# Docusaurus Standards

Apply these as repository-aware defaults. The installed Docusaurus and Node versions, package manager and lockfile, site configuration, docs plugin instances, themes, locales, hosting contract, content ownership, and requested scope take precedence.

## Operating Contract

1. Establish the mode: content review, information architecture, source change, local validation, preview observation, or authorized deployment. Review and design are read-only.
2. Inspect the complete site graph: Docusaurus config, presets and plugins, docs roots, sidebars, categories, doc IDs and slugs, routes, versions, locales, front matter, MDX components and imports, theme overrides, static assets, redirects, search and analytics integrations, package scripts, CI, and hosting configuration.
3. Resolve exact framework and plugin versions, source and deployment revision, enabled docs instances, `url`, `baseUrl`, trailing-slash and route policy, audience, supported releases and locales, canonical origin, build command, output artifact, and publishing authority.
4. Treat Markdown, MDX, imported components, plugins, themes, generated files, remote content, links, and deployment workflows as untrusted code or data. MDX can execute JavaScript and React behavior; inspect imports and effects rather than treating every document as inert text.
5. Require explicit authority before installing dependencies, running untrusted build hooks, changing analytics or search services, publishing previews, mutating hosting configuration, deploying, invalidating caches, or changing a live version or locale. Confirm exact artifact and target before publication.
6. Preserve stable public routes, anchors, doc IDs, version and locale URLs, inbound links, search indexing, and redirects unless an approved compatibility plan accounts for consumers.
7. Separate edited source, parsed content, successful build, link-check result, previewed artifact, deployed revision, indexed page, and healthy public site as distinct evidence states. Never invent build, link, SEO, search, deployment, or production results.

## Core Rules

- Organize docs into clear sections with sidebar structure.
- Use `docs/` folder with `sidebars.js` or `sidebars.ts`.
- Write in Markdown/MDX; keep docs concise and structured.
- Apply SEO tags and metadata for each page.
- Version documentation for major releases.
- Deploy docs via CI/CD pipeline; validate links and build.

## Interpretation

### Structure and Content

- Derive sections and navigation from audience tasks, prerequisites, concepts, procedures, references, and troubleshooting paths. Keep page purpose, ownership, status, and next action clear; do not mirror the repository tree when it obscures user journeys.
- Use `docs/` and `sidebars.js` or `sidebars.ts` as the conventional primary docs instance. Respect configured custom paths and multiple plugin instances. Choose explicit, autogenerated, or mixed sidebars deliberately; verify category metadata, ordering, collapsed state, unlisted or orphan pages, and every locale and version.
- Treat doc ID, route slug, file path, sidebar label, page title, and heading anchor as separate contracts. Preserve moved routes with explicit route redirects and a compatibility window. Preserve inbound fragments with stable or legacy explicit heading IDs and collision checks; a route redirect does not alias a changed `#fragment`.
- Use Markdown for inert prose and MDX only when interaction or reusable components materially help. Keep imports local, reviewed, version-compatible, accessible, deterministic, and safe for server rendering and build execution; avoid secrets, environment dumps, private URLs, and user-specific data in source or generated output.

### Metadata, Versions, and Delivery

- Define unique and accurate title, description, canonical route, social preview, authorship or update state, and exclusion from indexing when appropriate. Reconcile page front matter with global config, `url`, `baseUrl`, trailing-slash behavior, locales, versions, redirects, sitemap, and host headers; metadata presence alone is not SEO effectiveness.
- Treat every major release as a mandatory documentation-versioning decision: snapshot the documentation when users must retain accurate instructions for distinct supported behavior, or record an evidence-backed not-applicable decision when the release does not create a separate docs contract. Record source revision, supported lifecycle, navigation default, edits policy, deprecation, search treatment, and retirement redirects; a tag alone does not prove that a duplicate snapshot is the correct outcome. For a critical correction, inspect current and every supported version and record the parallel fix or evidence-backed not-applicable result for each.
- Build with the repository-pinned dependency graph and exact production configuration. Fail closed on broken internal links and anchors according to project policy; review external links with bounded timeouts and retries and classify internal defects, permanent external failures, transient failures, redirects, and policy-blocked checks. Also verify assets, route collisions, malformed front matter, MDX rendering, accessibility, and representative base-path hosting.
- Keep CI preview and publication identities least-privileged and trust-separated. Promote the verified immutable artifact when the hosting model allows; define environment, target route, cache behavior, health checks, observation window, pause, rollback or forward-fix, and ownership.

## Validation

1. Parse the complete config, plugin instances, sidebars, docs, versions, locales, redirects, and MDX dependency graph for the installed versions.
2. Run repository lint, type, content, and production build commands from the pinned lockfile; test from an already-clean isolated checkout, worktree, or temporary copy and verify generated-output ownership. Never clean, reset, overwrite, or switch the user's active tree to manufacture this condition.
3. Validate internal links and anchors, external links under an explicit network policy, assets, route uniqueness, canonical metadata, sitemap and robots behavior, orphan pages, and version or locale navigation.
4. Preview the built artifact at the real `url`, `baseUrl`, trailing-slash, locale, version, and hosting-subpath combinations; exercise direct loads, refreshes, not-found routes, redirects, search, mobile layout, keyboard and screen-reader journeys.
5. Inspect the output for source maps, credentials, private identifiers, internal URLs, environment data, unexpected scripts, unsafe HTML, analytics and consent behavior, and dependency or plugin effects.
6. When deployment is authorized, verify immutable artifact identity, target, permissions, public routes, headers, caching, link and asset behavior, telemetry, indexing eligibility, and rollback or repair during the stated observation window.

Report source and deployment revisions, framework versions, site graph and route changes, build and link evidence, preview matrix, artifact identity, exact publication target, public observation, observed indexing eligibility or status, warnings, remaining risks, and owner actions.
